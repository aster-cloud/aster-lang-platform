## 系统性模式（比单个 bug 更重要）

- **P1 · 双引擎语义分歧** — **头号系统性风险**。产品核心正确性卖点是 dual-engine Core IR parity，而分歧遍布词法/归一化/解析/类型推断每一层（INT/LONG 范围、全角→半角、`not` 优先级、Message/Dosage 规则）。根因：两套手写实现靠**人工+注释同步，无机器强制的 parity 契约**——注释写着"与 TS 一致"却已漂移。
- **P2 · 单源漂移** — 共享逻辑被复制成多份（TypeInference 规则、effects 前缀表、runner/API 错误分类、error_codes、词汇合并），靠硬编码列表或行号注释同步。
- **P3 · 数字字面量范围校验系统性缺失** — INT/LONG/FLOAT 在 AstBuilder、手写 Lexer、TS lexer 全无统一范围守卫，行为三态不一致（崩溃 / 静默 Infinity / 静默丢精度）。
- **P4 · 覆盖率度量造假/盲区** — 分类器误判（Date 被吞出分母）+ harness 静默跳过 + 文档陈旧 + 零错误路径覆盖，四者互相掩盖，把"伪 100%"合法化。**测量层本身不可信** = 修任何 parity bug 都无法证明修好了。
- **P5 · 静态门禁 allowlist 化，缺 deny-by-default** — CapabilityChecker（校验声明非行为）、effect_inference（前缀表）、effects.ts（硬编码）——静态安全门"未命中即放行"。真沙箱在 runtime，这些是 defense-in-depth 失效。
- **P6 · 未捕获 RuntimeException/Error 击穿编译管线** — NumberFormatException、StackOverflowError 逃过 `catch(Exception)`，把本应是结构化诊断的东西变成裸栈/500。

## 修复优先级

1. **evaluate-json 生产故障**（唯一"生产直接坏"的真故障，先删/改走 in-process）。
2. **度量诚实化（P4）**——否则 parity 修复无法验证；必须先让 gate 诚实。
3. **对齐 `not`/全角/字面量（P1 parity）**——先补 conformance 语料锁定，再统一实现。
4. **单源化 TypeInference 规则 + 数字范围校验原语（P2/P3，治本）**。
5. defense-in-depth 与技术债（P5/其余 Low）按排期。

#### HIGH-1. evaluate-json 运行期 fork Node CLI（aster-convert），生产镜像不含 Node → 端点整体不可用 

- **仓库**: `aster-api`（闭源）
- **位置**: `src/main/java/io/aster/policy/common/PolicySerializer.java:104-166, 315-340`
- **类别**: dead-code / abstraction-leak / ecosystem-reuse · **验证**: ✅ CONFIRMED
- **说明**: PolicyEvaluationResource.evaluateJson（src/main/java/io/aster/policy/rest/PolicyEvaluationResource.java:298-312）是一个仅受 enforceApiQuota 保护、无特性开关的 live 端点。它每次请求都调用 PolicySerializer.toCNL() 用 ProcessBuilder("node", cliPath, "json-to-cnl", "-") 外 fork 一个 aster-convert Node CLI 子进程来把 JSON 转成 CNL。resolveCliPath() 的解析链是: 环境变量 ASTER_CLI_PATH → 项目根 node_modules/.bin/aster-convert → dist/src/cli/policy-converter.js → 兜底裸字符串 "aster-convert"。而生产运行镜像最终阶段是 registry.access.redhat.com/ubi9/ubi-micro（Dockerfile:103）与 azul/zulu-openjdk-alpine:25-jre（Dockerfile.jvm:11），二者都不含 Node.js/npm/aster-convert（Node 只出现在 Dockerfile 的 build-time node-builder 阶段，Dockerfile:12）。因此生产容器里 resolveCliPath() 必然落到裸 "aster-convert"，ProcessBuilder.start() 抛 IOException → PolicySerializationException("Failed to execute aster-convert CLI")。这条 JSON→CNL 能力其实已由 in-process 的 DynamicCnlExecutor / Core-IR pipeline 覆盖（evaluate-source 路径全程 in-JVM，无子进程），evaluate-json 是一条与既有 in-process 能力重复、且在生产不可运行的自研外挂路径——违反‘生态复用/单一能力源’。
- **失败场景**: 生产容器中 POST /api/v1/policies/evaluate-json（合法 JSON policy body）→ toCNL 走到裸 "aster-convert" → ProcessBuilder.start() IOException → PolicySerializationException → 端点对所有请求返回 EvaluationResponse.error("CNL 策略执行失败: Failed to execute aster-convert CLI")，功能完全不可用，而等价的 evaluate-source in-process 路径正常。

#### HIGH-2. 类型推断:以 -age 结尾的字段被 Age$ 规则误判为 Int,且 message/dosage 与 TS 引擎产生 parity 分歧 

- **仓库**: `aster-lang-core`
- **位置**: `src/main/java/aster/core/inference/TypeInference.java:56`
- **类别**: parity-divergence · **验证**: ✅ CONFIRMED
- **说明**: Int 后缀规则 `(?:Count|Number|Qty|Quantity|Age|Score|...)$` 用 matcher.find() 且未加驼峰/词边界,`Age` 会匹配任何以 -age 结尾的英文单词(message、dosage、usage、language、package、damage、mileage、coverage...),把它们推断为 Int。更严重的是 parity:TS 参考实现 BASE_NAMING_RULES 含一条 Java 缺失的高优先级规则 `(?:Message|Dosage)$` → Text(priority 11),使 TS 中 errorMessage/dosage 推断为 Text;Java 无此规则,errorMessage/dosage 落到 Age$ → Int。同一字段名双引擎推断出不同类型,直接破坏本项目赖以保证正确性的 dual-engine Core IR parity gate。
- **失败场景**: 字段名 errorMessage:Java inferTypeNameFromFieldName 返回 Int,TS 返回 Text。dosage 同样 Java=Int / TS=Text。usage/language/package 等在两引擎均误判为 Int(共有缺陷)。已实测。

#### HIGH-3. stdlib_date 被误判为 eval-exempt，Date.* 合规原语零跨引擎执行覆盖(伪 100%) 

- **仓库**: `aster-lang-test`
- **位置**: `aster-lang-test/scripts/tag-eval-exempt.mjs:76,89`
- **类别**: test-coverage · **验证**: ✅ CONFIRMED
- **说明**: eval 覆盖率分类器 tag-eval-exempt.mjs 用硬编码白名单 STDLIB_NAMESPACES = {Text,List,Map,Maybe,Option,Result}(第76行)判定 `X.y(` 是否为受支持的 stdlib 命名空间调用。凡不在此集合内的 `[A-Z]\w*\.[a-z]\w*(` 一律在第89行 usesUnsupportedConstruction 里返回 `enum/type static method unsupported in both engines`,被标记为 evalExempt(reason=unsupported-syntax),从 eval-able 分母中剔除。但 `Date`(以及 `Decimal`)是两个引擎都真实实现的一等 stdlib 命名空间:TS 侧 aster-lang-ts/src/core/interpreter.ts:794 起实现 Date.fromISO/daysBetween/addDays/year/month/day,JVM 侧 aster-lang-truffle/src/main/java/aster/truffle/runtime/Builtins.java 实现同名 builtin。因此 manifest 样本 stdlib_date(整份跑 Date.fromISO/daysBetween/addDays/year/month/day,是合规/监管相关的日期算术原语)被静默归入 unsupported-syntax 豁免,从不参与跨引擎 eval-parity 比较。结果:node scripts/tag-eval-exempt.mjs 报 143/143 = 100% 覆盖,而实际该样本的日期运算在 parity gate 里零执行。stdlib_decimal 逃过同一 bug 仅仅因为有人手写了 .cases.json(第132行 `const ex = hasCases.has(name) ? null : exemptReason(...)`——有 cases 就跳过豁免判定);stdlib_date 没写 cases 就被吞掉。两引擎虽各有单引擎 Date 单测(值手工对齐),但无任何自动化机制把它们绑定为 parity,未来任一引擎日期实现漂移(如闰年/epoch 边界/时区)不会被 parity gate 捕获。
- **失败场景**: 运行 `node scripts/tag-eval-exempt.mjs`:stdlib_date 命中 usesUnsupportedConstruction 的 `Date.fromISO(` → 返回 unsupported-syntax → evalExempt=true → 从 143 分母剔除 → 报告 143/143=100%。真实情况:Date.* 日期算术从不跨引擎执行。若某引擎的 Date.addDays 在跨月/闰年边界算错(如 TS 返回 epoch-day X,Truffle 返回 X+1),parity gate 绿灯放行,合规日期计算(如 GDPR 保留期 waitElapsed >= 30 天)在两引擎产出不同结果而无人发现。

#### HIGH-4. 裸整数字面量超范围:TS 静默接受/丢精度,Java 抛 NumberFormatException(引擎语义分歧) 

- **仓库**: `aster-lang-ts`
- **位置**: `src/frontend/lexer.ts:623`
- **类别**: correctness/dual-engine-divergence · **验证**: ✅ CONFIRMED
- **说明**: TS 词法器对无 'L' 后缀的整数字面量用 `parseInt(num, 10)` 产出 JS number。JS number 是 IEEE-754 双精度:(1) 任何 > Integer.MAX_VALUE(2147483647) 的裸整数(如 `3000000000`)在 TS 被接受为普通 Int,而 Java 词法器 Lexer.java:620 用 `Integer.parseInt(num.toString())`(无 try/catch)对同一输入抛 NumberFormatException,直接拒绝/崩溃;(2) 任何 > 2^53-1(Number.MAX_SAFE_INTEGER=9007199254740991)的裸整数(如 `99999999999999999999`)在 TS 被静默截断为最近的可表示 double(实测变成 100000000000000000000),而 Java 拒绝。下游 lower_to_core.ts:494 `Core.Int(e.value)` 与 typecheck 均无范围守卫,错误值一路传到 Core IR / 求值,造成两引擎对同一源码产出不同结果或不同错误。对照:LONG 路径(lexer.ts:619)已刻意用 `BigInt(num).toString()` 保精度(见 lexer.test.ts:40 注释),证明 INT 路径的缺失是遗漏而非有意。
- **失败场景**: 源码含 `Return 3000000000.`(30 亿,超 Java int 上限)→ Java 引擎:词法阶段 NumberFormatException 拒绝该模块;TS 引擎:接受并当作合法 Int 编译执行 → 双引擎对同一输入行为分歧(一拒一收)。源码含 `Return 99999999999999999999.`→ TS 把该字面量静默变为 100000000000000000000(丢精度),Java 拒绝 → 结果/错误均不一致。

#### HIGH-5. `not` 运算符优先级双引擎分歧：Java 绑定紧于比较/算术，TS 绑定松于比较/算术 

- **仓库**: `aster-lang-ts`
- **位置**: `aster-lang-ts/src/parser/expr-stmt-parser.ts:871`
- **类别**: operator-precedence · **验证**: ✅ CONFIRMED
- **说明**: Java 语法把 NOT 放在 unaryExpr 层（AsterParser.g4 `unaryExpr : NOT unaryExpr # NotExpr`，AstBuilder.visitNotExpr 的操作数是 ctx.unaryExpr()），因此 `not` 的优先级高于比较、加减、乘除——`not` 只作用于其后的一个 unary/postfix 操作数。TS 手写递归下降把 `not` 放在 parseAnd 与 parseComparison 之间（parseNot 消费 `not` 后递归 parseNot→parseComparison），因此 TS 的 `not` 优先级低于比较和算术，会吞掉整个比较/算术表达式作为操作数。两侧对同一源码构造出结构不同的 Core IR（Call('not', ...) 包裹的子树不同），导致求值结果分歧。语料库未覆盖：现有 `not` 用例只有 `not Action.equals(...)`（`not <postfix 调用>`）这种形式，此时其后无比较/算术运算符，两引擎恰好一致，所以掩盖了分歧。DIVERGENT-MANIFEST.md 也未记录此项（其第126行提到的是历史 tokenise bug，非本优先级问题）。
- **失败场景**: 源码 `Return not x greater than y.`（x=1,y=2）：Java 解析为 `(not x) greater than y` = `(not 1) > 2`；TS 解析为 `not (x greater than y)` = `not (1 > 2)` = `not false` = true。两引擎对同一输入产出不同 IR 与不同布尔结果。同理 `not a plus b`：Java=`(not a) + b`，TS=`not(a + b)`。

#### HIGH-6. 全角转半角字符集不一致：Java 转换整个 FF01–FF5E 区间，TS 只转换字母数字+硬编码子集 

- **仓库**: `aster-lang-ts`
- **位置**: `aster-lang-ts/src/frontend/canonicalizer.ts:576`
- **类别**: unicode-normalization · **验证**: ✅ CONFIRMED
- **说明**: 两引擎的 fullWidthToHalf 都由同一 lexicon 配置开关门控（zh-CN.ts:105 `fullWidthToHalf: true`，中文词法表默认开启），但实现覆盖的字符集不同。Java fullWidthToHalfWidthImpl 对全角空格 U+3000 及整个全角 ASCII 区间 `！`–`～` 统一减 0xFEE0 转半角（覆盖全部全角标点/符号/数字/字母）。TS fullWidthToHalfWidth 只处理：全角数字 FF10-FF19、全角大写 FF21-FF3A、全角小写 FF41-FF5A（减 0xFEE0），外加一个硬编码运算符/括号列表 FF0B FF0D FF0A FF0F FF1D FF1C FF1E FF08 FF09 FF3B FF3D。凡是落在 Java 区间内、但不在 TS 子集内、且未被 normalizeCJKPunctuation 兜底的全角字符，两引擎会对同一源码产生不同 canonical 文本，进而 accept/reject 分歧或 AST 形状分歧。载荷字符至少包括：全角句点 `．`(FF0E)→Java 转成语句终止符 `.`、TS 原样保留；全角百分号 `％`(FF05)→Java 转 modulo 运算符 `%`、TS 保留；全角井号 `＃`(FF03)→Java 转注释标记 `#`、TS 保留；全角下划线 `＿`(FF3F)→Java 转标识符字符 `_`、TS 保留（改变标识符名）。
- **失败场景**: 中文词法表下源码 `模块 应用．`（用全角句点 U+FF0E 作句末符）：Java 先把 `．`→`.`，得到合法的 `Module 应用.` 可解析；TS 不转换 `．`，句末缺 ASCII `.`，报 `missing '.'`/moduleHeader 解析失败。一个引擎接受、一个拒绝，直接 parity 破裂。类似地 `ｘ ％ ２`（全角百分号）在 Java 变成 modulo 运算而 TS 变成未知字符；含全角下划线的标识符 `ｆｏｏ＿ｂａｒ` 在 Java 归一为 `foo_bar`、TS 归一为 `foo＿bar`（字母转了、下划线没转）→两引擎标识符名不同，运行时 context 键不匹配。

### 🟠 Medium（9）

#### MEDIUM-1. 整数/长整型字面量溢出导致 AstBuilder 抛出未捕获的 NumberFormatException （原 high → 验证后 medium）

- **仓库**: `aster-lang-core`
- **位置**: `src/main/java/aster/core/parser/AstBuilder.java:1515`
- **类别**: correctness · **验证**: ✅ CONFIRMED
- **说明**: 文法 INT_LITERAL: [0-9]+ / LONG_LITERAL: [0-9]+[Ll] 对位数无上限,但 AstBuilder 用裸 Integer.parseInt / Long.parseLong 转换。超过 Integer.MAX_VALUE(约10位)或 Long.MAX_VALUE(约19位)的字面量会抛出未捕获的 java.lang.NumberFormatException,直接击穿 AST 构建阶段,而非产出结构化诊断。受影响点:visitIntExpr(:1515)、visitLongExpr(:1559)、parseAnnotationValue(:549 INT / :557 LONG)、visitRetrySection(:869 max attempts)、visitTimeoutSection(:896)。与 FLOAT 路径(静默 Infinity)行为不一致,证明缺乏统一的字面量范围校验。

#### MEDIUM-2. 类型推断:布尔前缀规则无驼峰边界,把 canceledAt/validatedAt/wasteAmount 等误判为 Bool 

- **仓库**: `aster-lang-core`
- **位置**: `src/main/java/aster/core/inference/TypeInference.java:42`
- **类别**: correctness · **验证**: ✅ CONFIRMED
- **说明**: 最高优先级(11)的布尔前缀规则 `^(?:is|has|can|should|was|will|did|does|allow|enable|disable|active|valid|require)` 只锚定字符串开头,未要求前缀后是驼峰边界。任何恰好以这些字母序列开头的字段名都被判为 Bool,压过更贴切的 DateTime/Float/Int 后缀规则(优先级10)。canceledAt(can*)→Bool 而非 DateTime;validatedAt(valid*)→Bool;wasteAmount(was*)→Bool 而非 Float;isbnCode(is*)→Bool 而非 Text;requireLevel→Bool 而非 Int。此规则与 TS overlay(type-inference-rules.ts:19)逐字相同,故属两引擎共有的设计缺陷(非 parity 分歧),但仍是真实的错误类型推断,会给这些常见时间戳/金额字段生成错误的 schema 类型。
- **失败场景**: 字段名 canceledAt → 推断 Bool(应为 DateTime);wasteAmount → Bool(应为 Float);isbnCode → Bool(应为 Text)。已实测两引擎一致输出 Bool。

#### MEDIUM-3. 类型推断:Bool 后缀规则缺少 Success/Passed/Verified,与 TS 引擎 parity 分歧 

- **仓库**: `aster-lang-core`
- **位置**: `src/main/java/aster/core/inference/TypeInference.java:44`
- **类别**: parity-divergence · **验证**: ✅ CONFIRMED
- **说明**: Java 的 Bool 后缀规则(priority 8)为 `(?:Flag|Enabled|Disabled|Active|Valid|Approved|Rejected|Completed|Confirmed|Sufficient)$`,而 TS 参考(type-inference-rules.ts:20)在此基础上还含 `Success|Passed|Verified`。因此 loginVerified/taskSuccess/paymentPassed 在 TS 推断为 Bool,在 Java 无匹配落到默认 Text。同名字段双引擎推断类型不同,破坏 dual-engine Core IR parity。
- **失败场景**: 字段名 loginVerified:Java 返回 Text,TS 返回 Bool。taskSuccess、paymentPassed 同样 Java=Text / TS=Bool。已实测 Java 侧。

#### MEDIUM-4. Manifest capability deny/allow policy is only enforced against DECLARED caps, never against actually-used caps; bare @io functions bypass it entirely （原 high → 验证后 medium）

- **仓库**: `aster-lang-core`
- **位置**: `src/main/java/aster/core/typecheck/checkers/CapabilityChecker.java:368`
- **类别**: capability-escape · **验证**: ✅ CONFIRMED
- **说明**: checkManifestConstraints() is the single call site of ManifestConfig.isAllowed() (grep-confirmed: only CapabilityChecker.java:382 calls it). It (a) returns early unless func.effectCapsExplicit is true (line 369), and (b) iterates only over func.effectCaps — the caps the author *declared* (normalizeEffectCaps(func.effectCaps), line 372/376) — never over the capabilities actually inferred from the function body (collectCapabilities(func.body), which is computed separately at line 75 for the MISSING_IO check but never fed to the manifest). Net effect: the deny-list constrains declarations, not behavior. A function that calls a denied capability (e.g. Process.exec) but declares only bare `@io` — which sets effectCapsExplicit=false per AstBuilder.java:222 `effectCapsExplicit = !caps.isEmpty()` — is never checked against the manifest deny-list. Even with effectCapsExplicit=true, a function can declare an innocuous cap (e.g. Http), call Process.exec, and the manifest still only sees the declared Http. The EFF_CAP_MISSING check (line 125, also gated on effectCapsExplicit) would flag the undeclared Process, but the deny-list itself is orthogonal and unreachable for bare-@io code.
- **失败场景**: Manifest denies PROCESS. Author writes a function with header `It performs io` (bare @io, no explicit capability list) whose body calls Process.exec(...). effectCapsExplicit=false → checkManifestConstraints returns at line 369 → manifest.isAllowed(PROCESS) is never called → no E027 diagnostic. The denied PROCESS capability passes the manifest gate. (Since core is diagnostic-only and, per StabilityGate.java:17-18, the aster-api production path does not run typecheck at all, this manifest gate is the compiler's only capability-policy enforcement and it is silently skippable.)

- **仓库**: `aster-lang-test`

- **说明**: `collectEffects`/`checkEffects`(Node 与 browser typecheck 主路径均调用,见 module.ts:265、browser.ts:417)使用从 pure.ts import 的**硬编码** `IO_PREFIXES`/`CPU_PREFIXES` 常量判定调用是否有 IO/CPU 效应。而效应推断模块 effect_inference.ts:55 用 `getIOPrefixes()`/`getCPUPrefixes()` 从 config 动态读取(effect_config.ts:310)。默认配置下两份前缀等价,但一旦用户通过 config 注入自定义 IO 前缀(effect_config.ts 支持 http/sql 分类扩展),效应*推断*会识别该前缀而效应*检查*不会——导致:自定义前缀的调用被推断为 IO 效应写入签名,但 checkEffects 观测不到该效应,`@io` 声明校验(EFF_MISSING_IO / EFF_SUPERFLUOUS_*)按错误的观测集裁决,产生假阴/假阳诊断。
- **失败场景**: 用户配置自定义 IO 前缀 `Payment.` 后,函数体调用 `Payment.charge(x)` 且未声明 `@io`:effect_inference 认定其为 IO 效应(按 config),但 checkEffects 用硬编码前缀集观测不到 `Payment.` → 不报 EFF_MISSING_IO,漏掉本应要求的 @io 声明;反之若函数声明了 @io 而体内只有自定义前缀调用,checkEffects 观测 observed 为空 → 误报 superfluous。

#### LOW-12. search 命令将远程包 manifest 的 description 原样打印到终端(ANSI/终端注入) 

- **仓库**: `aster-lang-ts`
- **位置**: `src/cli/commands/search.ts:179`
- **类别**: terminal-injection · **验证**: ✅ CONFIRMED
- **说明**: searchRemote→downloadManifest→readManifestFromTarball 从远程 GitHub release 下载 tarball,用裸 JSON.parse 读取 manifest.json(search.ts:170),完全绕过 manifest-parser.ts 的 Ajv schema 校验。取出的 description 字段(攻击者可在自己发布的包 manifest 里任意控制)在 printResults() 中经 `console.log(...| ${item.description})` 直接写入 stdout,未做任何控制字符/ANSI 转义过滤。恶意 description 可含 ANSI 转义序列执行光标操纵、清屏、伪造输出行,在部分终端还可触发标题设置/剪贴板等 OSC 序列。相较 install 路径,search 会对候选包(含 `aster.<keyword>` 自动拼接的名字)主动拉取并打印描述,受害面是任何运行 `aster search <kw>` 的开发者。
- **失败场景**: 攻击者发布名为 `aster.leftpad` 的包,manifest.description = "\x1b[2J\x1b[H 伪造的安全提示..."。开发者运行 `aster search leftpad`,CLI 自动把 `aster.leftpad` 作为候选拉取其 manifest 并 console.log 其 description,终端被清屏并显示攻击者伪造的内容(如伪造的『已验证/官方包』字样诱导安装),或注入 OSC 序列操纵终端状态。

#### LOW-13. 效果推断基于函数名前缀,非前缀命名的 IO builtin 被静默判为无副作用 

- **仓库**: `aster-lang-ts`
- **位置**: `src/effects/effect_inference.ts:231`
- **类别**: effect-inference-soundness · **验证**: ✅ CONFIRMED
- **说明**: recordBuiltinEffect() 仅当被调 builtin 名称以配置前缀(effect_config.ts DEFAULT_CONFIG:`IO.`、`Http.`、`Db.`、`UUID.randomUUID` 等一小撮)开头时才标记 IO/CPU 效果。任何执行真实 IO 但名称不在前缀表、且既非本地函数(index.has)又无导入效果签名(importedEffects)的 builtin,localEffects 为空=被推断为 pure,inferEffects 不会产出 EFF_INFER_MISSING_IO,能力/效果门禁看不到该 IO 使用。此外 loadEffectConfig 允许经 ASTER_EFFECT_CONFIG 用运营者提供的 JSON 覆盖前缀表:validateStringArray 对空数组回退默认(安全),但可用非空数组整体替换掉真实前缀(如把 io.http 改成 ['ZZZ.']),从而让 `Http.get` 不再被识别为 IO。该 pass 是 TS 侧编译期静态辅助诊断,真正的运行时沙箱在 aster-api/truffle(不在本切片),故为可靠性/软soundness 缺口而非本仓可直接触发的沙箱逃逸。
- **失败场景**: 策略调用一个执行网络请求但命名为 `Webhook.post`(不在任何 IO 前缀表)的 builtin,且未提供其导入效果签名。inferEffects 推断该函数 pure、不报缺 @io;若下游能力门禁依赖推断出的效果集来判定是否需要 HTTP 能力,则该网络 IO 在 TS 侧静态检查中不可见,漏报。运营者亦可通过 ASTER_EFFECT_CONFIG 提供替换性前缀表进一步扩大该盲区。
